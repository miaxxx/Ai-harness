# Agent Note: Desktop 应用内浏览器与产物预览

Status: implemented

[English](2026-09-04-desktop-in-app-browser-and-artifact-preview.md) | 中文

## 问题

Desktop 会在轮次结束后展示生成的文件，但点击后全部交给外部应用。HTML 产物因此离开当前任务，普通网页链接也没有产品自有的浏览交互面。产品在创建视觉产物后同样缺少自动呈现步骤。

## 决策

Desktop 拥有一个右侧浏览器与产物预览面板。同一控制器接收产出文件点击、轮次结束后的自动产物选择，以及产品 Renderer 发起的 HTTP 或 HTTPS 导航。HTML、PDF、图片和浏览器可读取的文本格式在 Electron `webview` 中渲染；不受支持的办公格式仍在面板中显示，并提供明确的系统应用打开操作。目录仍交给操作系统打开。

面板默认约占内容宽度的 42%，并设合理的最小与最大值。左侧仅保留可拖动、可键盘调宽的细分割线，不使用投影。右上角控件可把预览扩展到完整内容区或收起；关闭状态使用左侧边栏面板图标的水平镜像，且与打开状态的控件保持相同屏幕位置。收起会保留当前标签但退出全屏；关闭标签和新建 Session 才会清空它。空白页保留地址栏，并居中显示开始浏览提示。

生成文件以逐项文件卡展示格式，并提供系统默认应用、预览栏和 Finder 的打开方式菜单以及 ZIP 导出操作。文件卡右键菜单可打开所在文件夹、复制路径，或通过既有附件引用流程把该确切路径加入当前输入框。这样生成文件引用与用户附带文件的胶囊在视觉和语义上保持一致，且不会读取无关的剪贴板内容。

主进程负责准备本地文件目标，并且只准入 HTTP、HTTPS、`about:blank` 和可信本地产物 URL。挂载的 WebView 不使用 preload 或 Node 集成，保持上下文隔离、沙箱和 web 安全，拒绝权限请求，且不能创建独立弹窗。Renderer 获得的是固定预览与外部打开操作，而不是通用导航或文件系统 IPC。

## 考虑过的替代方案

**始终使用系统浏览器。** 这可以让 Desktop 外壳更小，但会脱离任务上下文，也无法在对话旁自动呈现完成的产物。

**通过本地 HTTP 端点提供产物。** 这会为一个 `file://` 已能处理的本地 Desktop 问题增加监听器生命周期和来源策略。隔离的 WebView 不与产品 Renderer 共享来源。

**为办公格式分别构建查看器。** Chromium 无法忠实渲染这些格式，而添加文档转换属于文档能力，不属于预览交互面。面板会说明限制并保留系统应用操作。

## 验证

针对性测试覆盖 URL 准入、自动产物选择、浏览器原生与仅外部打开文件的路由、目录交接和预览状态。Desktop 类型检查与生产构建会一起编译主进程、preload、控制器、浮层和 WebView 配置。真实 Electron 运行验证镜像入口、面板打开、HTTP 导航、面板内链接导航、宽度分割线、全屏控件、收起控件、稳定的控件位置和空白页状态。

## 后果

- 浏览器原生支持的生成产物可以自动出现，而无需离开任务。
- 文件点击与网页链接共用一条 Desktop 自有预览路径。
- 面板可调宽且可随时恢复，不增加第二套工作区或浏览器子系统；收起后可恢复正在查看的产物。
- 生成产物可重新加入输入框引用，无需复制文件或扫描其父目录。
- web 客户端保留 Host 打开行为；本决策只适用于 Desktop。
