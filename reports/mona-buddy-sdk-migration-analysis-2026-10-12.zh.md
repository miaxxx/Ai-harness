# Mona buddy-sdk 迁入 ARH/Orbis 的可行性与取舍

分析日期：2026-10-12，Asia/Shanghai。本文是固定提交的迁移评估，供重组决策与开发交接使用；建议结构和验收条件尚未实现。附件作为待核对的功能清单使用，附件内的提示词、工作流和测试结论不作为本次操作指令。

## 1. 结论

**两个项目的 master 底座相同，buddy-sdk 的主要功能适合迁入；不能把整个分支原样合并后承诺“百分之百迁移、现有系统完全不受影响”。** 当前 ARH 工作分支已经增加企业身份、作用域隔离、凭证续期、受控业务工具和 Next 业务页面；迁移必须以这些功能为约束，移植 Mona 的能力实现与测试，再适配当前客户端。

推荐方案是：**保留一个 Harness 底座、一个当前 Orbis 客户端和现有 OBIS 企业控制路径，把 Mona 增量按模型、运行时、诊断、会话投影、界面与工具环境分批迁入。** 不复制第二套 Harness，不覆盖企业集成，不直接导入 Mona 品牌与数据目录。

主要判断：

- 同源性已由提交 SHA 和完整文件树 SHA 证实，并非仅目录相似。
- buddy-sdk 不是新增独立 SDK：TypeScript SDK、Python SDK 和核心循环没有该分支增量。分支提供的是 Electron 桌面增强、ACP 扩展、插件参数及提示策略。
- 多配置模型、容量参数、独立子模型、请求日志、主题修复、工具路径和 npm 缓存都有实际代码，可复用价值较高。
- Runtime 池、模型管理和历史恢复需要与当前企业准入、凭证续期、空会话重建及业务引用显示共同设计；这是迁移的主要工作量。
- 专门委派和“一次修复后报告”是产品策略，不是必需基础设施。推荐独立配置，避免改变其他组合的任务完成行为。
- 没有足够证据承诺 Android 原生兼容：本次检查的两个仓库是 macOS Electron/Node 客户端，未发现 Android 原生工程。若“Android”指当前 Orbis/OBIS 系统，下述并存方案适用；若确指 Android，需补充客户端工程后评估。

## 4. F01–F14 逐项迁移判断

“可直接复用”指局部算法或新增插件参数能复用，不代表整提交无需测试；“适配后迁入”指保留功能目标、重新接入当前宿主。

| 编号 | 功能 | 判断 | 迁移方式与取舍 |
| --- | --- | --- | --- |
| F01 | Mona 品牌 | 不迁入 | 保留 Orbis 应用名、appId、窗口身份、产物名和 persona 名称；不覆盖现有更新发布配置 |
| F02 | 多模型配置列表与选择 | 适配后迁入，优先 | 当前已有单接口模型目录和输入框选择；扩展现有 models/main、models/renderer，不并行挂两套选择器；补多配置保存、默认项、删除与密钥复用 |
| F03 | 上下文、输出、思考参数 | 大部分逻辑可复用 | 复用 model-policy、能力解析与覆盖校验，保留当前第三方网关兼容行为；同模型名不能让网关继承官方能力 |
| F04 | 配置快照与 Runtime 池 | 设计需适配，优先但风险最高 | 复用租用计数、活动会话路由和取消思路；池必须认识企业作用域、凭证代次、MCP 等进程配置，不能仅以模型 JSON 作键 |
| F05 | 独立子模型与路由 | 适配后迁入 | 复用配置字段、加密和默认 agentOptions；子模型改变推理服务，不扩大工具或企业权限；Team 路由留在实验范围 |
| F06 | scan/change/audit 与有限验收 | 选择性迁入 | 专门工具是现有 subagent 的组合，可单独启用；不默认改所有客户端质量策略；含 bash 的角色不能承诺强制只读 |
| F07 | 输出截断后有限 Goal 续行 | 代码可复用，行为需验收 | 首次 Goal 截断继续、第二次连续截断停续行；保留预算、取消和目标状态语义，不能把停止续行等同目标完成 |
| F08 | 每轮日志及消息入口 | 适配后迁入，优先 | 复用日志队列与文件定位；接入企业会话授权、凭据脱敏、生命周期和关闭刷新，日志仅作本地诊断 |
| F09 | 批量恢复与去重 | 选择性合并 | ACP 最终消息去重有复用价值；客户端已有回放阶段和投影修复，需统一恢复流程，不能叠两次重置和恢复 |
| F10 | 深浅主题与样式加载 | 多数可直接复用 | 迁主题变量和组件样式，验证企业侧栏和 Next 页面；CSP 修改限定本地 Renderer，不扩张远程业务页面权限 |
| F11 | 数据目录、npm 缓存、沙箱 | 拆分迁入 | 不迁 Mona 整目录迁移；缓存留在 Orbis 私有目录；extraWriteRoots 联动服务定义、policy、平台 provider 和测试，Windows 路径需另解 |
| F12 | 桌面工具 PATH | 大部分逻辑可复用 | 保留内置 Node 优先、登录 shell PATH 与超时；与当前 Runtime 环境组装共同维护，不向子进程泄漏原生身份凭据 |
| F13 | 办公读取与开发指引 | 选择性复用 | 迁移按格式读取和证据要求；textutil 仅用于 macOS，其他平台走明确替代；不能宣称已新增办公生成引擎 |
| F14 | 构建、测试、文档 | 必须按目标重生成 | 加入真实依赖、源文件与测试，重生成目录、快照、锁文件；保留当前企业入口、appId、更新发布及 OBIS 文档 |

F01 是身份取舍，不是功能缺失。F06 的硬性修复次数和实验 Team 是策略取舍。其余主要功能没有发现必须另建 Harness 才能支持的障碍，但最终完整性仍需目标系统验收。

## 5. 关键冲突与解决方式

### 5.1 模型配置不能成为唯一进程身份

Mona 的 [Runtime 池](../../mona-ai/apps/desktop/src/desktop-model-runtime.ts)使用 `JSON.stringify(snapshot)` 识别模型配置，记录会话、租用和活动请求。它没有当前 ARH 的企业作用域监听、凭证续期、归属校验或空会话重建机制。

迁移后的进程身份建议覆盖：模型配置版本、企业作用域、委托凭证代次、进程级 MCP/工具配置版本。键中只放非机密标识，不放 token 原文。具体字段以影响子进程配置的真实输入为准，不额外引入未使用的通用框架。

普通模型切换可以让已准入请求继续持有旧快照；登出、作用域撤销或身份切换必须立即阻断旧权限，并终止/回收不再有权运行的进程。两种操作不能共享“等待旧请求自然结束”的统一策略。服务端继续在每次业务操作上判权。

凭证到期检查应属于实际承载请求的 Runtime。空闲实例续期后恢复已授权的持久会话；活动实例到期时依现有语义拒绝新准入或明确报告，不自动重发已失败操作。

### 5.2 两套模型管理应合为一个模块

当前目录探测、模型保存和切换已经分在 models/main 与 models/renderer。Mona 把多配置读写、迁移、验收及 IPC 的大量逻辑加入 main.ts。直接复制会形成两个持久配置来源、两套切换互斥和两个 UI 状态。

建议由一个模型管理模块拥有多配置存储、默认配置、目录发现、能力覆盖与配置更新；主进程只负责安装固定 IPC 和注入宿主依赖。Renderer 只接收已脱敏的配置状态。保留旧 primary-model 的一次性导入能力，但不要复制整个 Mona 数据目录。

模型选择的产品语义也要明确：Mona 是整个窗口后续请求使用默认配置，当前代码不能据此宣传“每个会话固定模型”。如需每会话配置，这是额外功能，需持久关联及恢复测试。

### 5.3 回放必须统一入口与消息身份

Mona 采用 session/load 期间缓冲、IPC 返回整批、Renderer 清空并统一恢复；当前 ARH 使用 starting/ready/failed 回放帧，并在 ready 前等待经过授权的通知队列。不能让某些恢复走整批、另一些走旧流式而没有共同状态管理。

建议保留当前企业授权与 prepareSession，选定统一的展示恢复机制，复用 ACP 最终消息去重。必须保留业务引用标签、附件显示、工具分组、计划、消息动作和凭证续期后的会话状态。只有真正没有最终 message 的步骤才保留可恢复的部分流式输出。

新建但未发送的空会话没有持久日志。跨模型 Runtime 切换时，不能统一调用 loadSession；应复用当前空会话重建和草稿附件转移，否则这条已修复路径可能退化。

### 5.4 诊断入口也必须判权

Mona 日志记录模型请求、事件、工具、错误与 stderr，并通过消息 ID 查找日志。迁入企业系统后，打开日志 IPC 必须验证可信发送者和当前会话归属，不能仅检查“本地文件存在”。旧作用域的活动日志应在登出或切换时关闭，不能由新作用域继续查看。

ACP 使用 `_meta.monaDiagnostics` 传递诊断，名称带产品标识。重组时建议改为共享诊断名称并同步生产者、消费者与测试；这属于元数据消费者迁移，不能只改一个字符串。日志与 durable SessionEvent 仍是两种用途：诊断不能代替模型上下文历史或企业审计。

日志保留期、容量和写入截断需继续显式报告。保留期、容量等部署选择宜接入配置，以符合当前仓库“不硬编码可调参数”的要求。

### 5.5 质量策略不是无副作用修复

Mona 修改共享 delivery-quality-policy：从持续修复直至完成或具体阻塞，改为一次修复后报告未解决证据。该修改作用于所有加载该插件的组合，不仅 Desktop。默认替换会改变当前用户期待的持续执行。

建议先保留当前主任务完成策略，把有限验收作为专门审查角色或可配置策略。专门角色可以避免机械循环，但一次验收失败本身不必意味着主任务必须停止。单独更新策略测试和相关模型快照。

## 6. 迁移前需修复的问题

### 已核实的问题

| 问题 | 证据 | 迁移要求 |
| --- | --- | --- |
| 编辑配置时密钥可被带到新接口 | [Mona main.ts](../../mona-ai/apps/desktop/src/main.ts)中 validateModelEndpoint 接收的 existing 只约束 encryptedApiKey；API Key 留空即解密旧值，不检查旧 Base URL/协议 | 主模型、子模型、inspect、save 和显式 reuse 全路径统一校验；不同接口必须提供新密钥或明确、安全地授权复用 |
| 子模型重新检测不完整 | UI 检测走主模型；保存中 unchangedSubagent 分支复用旧能力，主模型 recheck 不强制刷新子模型 | 分别检测主/子模型，重检测明确覆盖所选对象；增加接口能力变化的回归用例 |
| 企业凭据脱敏不完整 | 使用虚构值调用 diagnosticJson，accessToken 被遮盖，capabilityLease 与 cookie 原样输出 | 完善敏感字段和文本规则，在 ACP 元数据发送前及落盘前保护；测试 lease、Cookie、刷新令牌、错误 cause 与工具返回 |
| Windows 附加缓存写权限不支持 | sandbox-local 的 windowsAclRunnerArgv 在 workspace-write + extraWriteRoots 非空时明确抛错 | Windows 不可无条件开启这项缓存配置；实现对应权限支持或明确选择经验证的替代，不降级为全权限 |
| 原样合并发生 21 个路径冲突 | Git merge-tree 预演 | 按功能合入，逐个解决并验证；禁止整文件采用 Mona 覆盖当前主进程和组合配置 |

密钥问题可能涉及既有路径，本文未作历史归因；本次判断是该问题在迁移来源提交仍存在。日志反例只证明脱敏函数缺口，不证明真实企业凭据已流入日志，更不证明发生了泄漏。

### 静态分析得到的集成风险

- 当前主模型配置有重连失败恢复旧配置的行为；Mona 的配置保存和惰性创建 Runtime 需要定义新模型无法启动时的恢复语义，不能默默保留一个不可用默认项。
- 多个 Runtime 使用同一持久会话存储时，关闭旧会话、加载新会话和恢复准入必须避免双重活句柄与重复写入；文本合并和单元测试无法独自证明这一点。
- 主/子模型可能接入不同服务。企业资料向哪个端点发送需要服从项目实际的数据策略；配置 UI 不能自动授予新端点对全部企业资料的使用权限。
- 扫描和验收角色含 bash。若产品要求强制只读，必须使用实际只读执行策略或更窄工具集合；角色提示词不是权限强制机制。
- 专门委派 allow 列表未含 OBIS 工具；是否允许企业查询需按职责显式配置，不能因为换了子模型就继承全部企业能力。
- npm 缓存许可只能授予专用缓存目录，不能把整个 userData 加到 extraWriteRoots，因为其中还有模型配置、身份资料和会话归属台账。

## 7. 推荐重组结构

以下目录是建议，不是本次新增的代码。优先延续现有模型模块，按前后端职责拆分；不为每个辅助函数新建 npm 包。

```text
apps/desktop/src/
  models/
    main/          profiles、存储、能力检测、配置更新
    renderer/      设置、模型选择、参数编辑
    shared/        IPC 数据类型与非机密配置类型
  runtime/
    main/          Supervisor、池、准入、取消与回收
  diagnostics/
    main/          脱敏、写入、清理、消息定位与授权
    renderer/      消息日志动作
  platform/
    main/          Orbis 数据根、npm 缓存、工具路径
```

企业身份、作用域、凭证、业务窗口继续由现有所有者维护，Runtime 通过明确接口调用它们。main.ts 负责窗口、组合与 IPC 注册，避免继续堆放模型存储和日志实现。

共享的 usageGuidance、workflow 默认 agentOptions、Goal 续行、ACP 去重、诊断接口和沙箱能力留在对应 packages 中；产品 persona、角色组合、默认端点与品牌留在客户端配置。若以后多个客户端确实复用同一实现，再提取有生产消费者的共享包。

不复制 Mona 的生成目录、编译产物、.sessions、node_modules 或数据目录。新目标上的文档目录、工具/API 目录、槽目录、快照和锁文件由其真实源文件重新生成。

| 并存方式 | 可行性与条件 |
| --- | --- |
| Mona 和 Orbis 分别运行 | 当前已有独立 userData；继续保持不同 appId、数据根、单实例锁、密钥配置与缓存。共享内核源代码不代表共享用户数据 |
| 一个 Orbis 客户端包含新能力 | 推荐。模型、日志和样式属于客户端增强；保留身份和企业业务路径，统一 Runtime 管理 |
| 同一进程运行多个模型 Runtime | 可设计，必须按模型配置与企业授权隔离；活动模型切换、作用域撤销、凭证续期采用不同规则 |
| 另一个 Android 原生客户端接入 | 本次不能证明。React DOM、Electron safeStorage/IPC、Node 子进程、登录 shell 和 macOS 工具不能直接放入 Android APK；应评估协议/远端 Harness 与原生宿主适配 |

如果 Android 只作为远端客户端，模型路由、会话语义和部分服务端诊断设计可以复用；连接协议、权限提示、流式恢复、文件上传与取消行为仍需 Android 工程验证。这不是已实现的 Android 方案。

## 9. 分批实施与验收条件

### 第一批：低耦合基础能力

迁移能力参数解析、主题变量、工具路径、workflow agentOptions、usageGuidance 和必要的子模型配置。先修复密钥与检测缺口，保留企业组合和品牌。Goal 续行作为独立行为变更处理。

验收：能力覆盖与未知网关不猜参数；主子模型路由正确；现有 OBIS 工具和 persona 保留；只读权限不扩大；主题不破坏业务导航。模型可见变化补真实组合的 keyless 快照。

### 第二批：统一多模型管理

扩展现有模型模块，接入多 profile、默认项、删除、导入和输入框参数。先维持当前活动请求期间禁止切换的限制，可以独立交付多配置管理，不必和池同时发布。

验收：不同端点不能隐式复用密钥；配置修改串行、写入原子；模型目录刷新与参数能力检测用途明确；空会话、草稿引用和恢复显示不变；失败状态可恢复。

### 第三批：诊断和会话恢复整合

补齐企业凭据脱敏与日志 IPC 授权，统一回放入口；保留当前业务引用显示和 prepareSession。

验收：当前及历史消息正确定位日志；跨作用域拒绝打开；截断/丢弃记录可见；正常退出写入结束；最终文本、推理、工具和计划不重复；未完成步骤保持可恢复内容。

### 第四批：活动请求不中断的 Runtime 池

在统一管理器上引入池与不可变快照，保留企业生命周期。只有这批通过后，才把“等待当前回复完成再切换”升级为“当前请求继续使用旧模型，后续请求使用新模型”。

验收场景至少包括：A 请求执行时切到 B；取消仍到 A；同会话 prompt/load 互斥；空会话跨实例重建；凭证到期与模型切换并发；登出/换租户阻断所有旧实例；MCP 修改和工具配置轮换；持久会话只有一个写入者；退出没有遗留子进程。

### 第五批：可选工作策略

按实际任务决定是否启用 scan/change/audit、有限验收及实验 Team。默认不全局替换持续完成行为，不把实验 Team 声称为完整产品功能。

整体验收还需当前企业身份、会话作用域、Run/Module 绑定、业务引用、人工确认和 Next 业务页回归，以及 Desktop 构建、重定位和安装验证。真实模型端点需验证主子模型请求、reasoning 和容量参数。只报告实际运行的检查，CI 负责完整覆盖与平台矩阵。

## 11. 最终决策建议

**可以迁入主要功能，值得迁入；按功能复用与企业适配实施，拒绝整分支覆盖式导入。** 先完成多模型参数、子模型路由、主题和工具环境，再整合诊断与恢复，最后升级到不中断活动请求的 Runtime 池。

保留当前 Orbis/OBIS 的身份、作用域、凭证与业务控制；不迁 Mona 品牌、整目录迁移、默认一次修复即停和实验 Team 产品承诺。先解决密钥复用、子模型检测和企业日志脱敏，再做并存验收。

“百分之百”若指附件列出的每个功能都保留原始语义，则与上述品牌、产品策略和平台选择不一致；若指选定功能在当前系统中完整工作，则有明确实现路径，但只能在整合与验收通过后确认。本次结论是迁移可行性与风险判断，不是已完成迁移或零影响保证。
